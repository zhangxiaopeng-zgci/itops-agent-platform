# AIOps Platform 信息架构收口计划

日期：2026-06-29

## 背景

当前平台已经具备主机、Kubernetes、网络设备、Hermes、Case、审批、任务、进化治理和平台运维等能力，但使用路径仍容易显得散乱：

- 全屏监控大屏仍偏主机视角，未把 Kubernetes、网络设备、闭环处理和拓扑准确性作为一等态势对象。
- 运维工作台的核心链路存在，但用户容易把资产入口、诊断入口、Kite/Hermes/拓扑能力入口混在一起理解。
- 平台控制台把 Hermes、进化治理、平台运维、设置放在同一层，缺少“智能能力 / 进化治理 / 平台运维”边界。

本计划的目标是收口信息架构，不再单纯新增入口。

## 总原则

1. **入口按任务组织，不按技术能力平铺**
   - 资产类入口从“资源与连接”进入。
   - 问题类入口从“诊断中心 / Case 工作台”进入。
   - 执行动作从“执行中心”进入。
   - 平台配置和治理从“平台控制台”进入。

2. **Kite、Hermes、拓扑是上下文能力，不是到处出现的一级菜单**
   - Kite 在 Kubernetes 资产上下文、诊断上下文、Case 上下文中出现。
   - Hermes 在诊断、修复、复盘上下文中出现。
   - 拓扑在资产关系和影响分析上下文中出现。

3. **大屏展示全栈态势，不只展示主机**
   - 主机、Kubernetes、网络设备、闭环处理、拓扑准确性、自动化状态都要有位置。
   - 主机网卡流量和网络设备健康是两类不同对象，不能混在一个“网络”指标里。

4. **平台控制台按治理边界分区**
   - 智能能力配置：Hermes、Channel、Agent、Skill、MCP、工具策略、模型。
   - 进化治理：提案、评估、回放、审批、发布、运行态版本。
   - 平台运维：健康检查、备份恢复、审计、用户、系统设置。

## 目标信息架构

### 首页 / 今日运维工作台

首页回答：“我今天要先处理什么？”

保留：

- 全局运维态势
- 从这里开始
- 建议下一步
- 待处理事项
- 进化提案摘要

优化：

- 首页态势卡点击进入上下文页面，而不是新增一级导航。
- Kubernetes 态势卡进入 Kubernetes/Kite 内嵌控制台。
- 网络设备态势卡进入网络设备资产页。
- 闭环处理进入 Case 工作台。

### 运维工作台

主线固定为：

```text
资源与连接 -> 诊断中心 -> Case 工作台 -> 执行中心
```

含义：

- 资源与连接：资产、凭证、连通性、主机/Kubernetes/网络设备关系。
- 诊断中心：告警、资源、Kubernetes、网络设备等上下文诊断入口。
- Case 工作台：把问题纳入闭环，聚合证据、状态、审批、任务和时间线。
- 执行中心：审批、任务、执行日志、验证修复。

不放入运维工作台一级导航：

- Kubernetes 控制台
- Kite
- Hermes Channel
- 拓扑
- 进化治理

这些能力应从上下文页面触发。

### 全屏监控大屏

从“主机监控大屏”演进为“全栈运维态势大屏”。

第一版分区：

- 总体健康：主机、Kubernetes、网络设备、告警、任务、审批。
- 主机资源：CPU、内存、磁盘、负载、指标新鲜度。
- Kubernetes：集群、节点、Pod、异常 Pod、Warning Event、节点背后主机绑定率。
- 网络设备：总数、在线、告警、离线、未知。
- 闭环处理：告警、Case、审批、任务、Hermes 会话、进化提案。
- 拓扑准确性：有效关系、过期关系、未绑定 K8s 节点、准确性分数。

后续可扩展：

- 网络接口状态、端口错误包、丢包、时延。
- 业务与用户体验层指标。
- 自动巡检和自愈运行状态。

### 平台控制台

平台控制台不再只是菜单集合，而是治理入口。

分为三块：

1. 智能能力配置
   - Hermes 控制台
   - Hermes Channel
   - Agent 管理
   - Skill / MCP
   - 工具策略
   - 模型配置

2. 进化治理
   - 进化提案
   - Evaluation
   - Staging Replay
   - Approval
   - Publish
   - Release 运行态

3. 平台运维
   - 生产就绪
   - 健康检查
   - 备份恢复
   - 审计日志
   - 用户权限
   - 系统设置

## 实施阶段

### IA-1：导航和入口边界收口

目标：减少一级入口混乱。

工作项：

- 保持运维工作台一级导航为 4 个入口：资源与连接、诊断中心、Case 工作台、执行中心。
- 不把 Kubernetes/Kite 放入运维工作台一级导航。
- 首页态势卡作为上下文跳转入口。
- 检查重复入口文案，统一“内嵌 Kite 控制台”“Hermes 诊断”“查看拓扑”等表达。

产出：用户知道从“资源、诊断、Case、执行”四条主线进入。

### IA-2：全栈监控大屏第一版

目标：大屏从主机视角升级为全栈态势。

工作项：

- 接入现有 `/api/dashboard/ops-overview`。
- 增加 Kubernetes 态势卡：集群、节点、Pod、异常 Pod、Warning Event、绑定率。
- 增加网络设备态势卡：总数、在线、告警、离线、未知。
- 增加拓扑准确性和闭环处理卡片。
- 保留主机 CPU/内存/磁盘/网络趋势。
- 文案从“资源监控”调整为“全栈运维态势”。

产出：大屏能展示主机、Kubernetes、网络设备和闭环态势。

### IA-3：运维工作台主流程强化

目标：让用户进入平台后知道怎么用。

工作项：

- 首页“从这里开始”明确为 4 步：资源与连接、诊断中心、Case 工作台、执行中心。
- “建议下一步”只展示可执行动作，不展示配置入口。
- 资产上下文中嵌入 Kite、拓扑、Hermes 入口。
- 诊断上下文中嵌入 Case 创建 / 关联入口。
- Case 上下文中嵌入审批、任务、验证、复盘入口。

产出：用户从问题到闭环有清晰路径。

### IA-4：平台控制台重构

目标：平台控制台按治理边界分区。

工作项：

- 平台控制台页面改成三块：智能能力配置、进化治理、平台运维。
- 侧边导航保持少量主入口，不把所有高级功能展开。
- 将 Hermes Channel、Agent、Skill、MCP、模型配置归入“智能能力配置”。
- 将进化提案、评估、发布、运行态版本归入“进化治理”。
- 将健康、备份、审计、用户、设置归入“平台运维”。

产出：平台控制台不再像功能列表，而像治理驾驶舱。

### IA-5：自动化闭环展示

目标：让平台体现 AIOps 的自动化，而不是只靠人工点击。

工作项：

- 在首页和大屏展示自动巡检、自动发现、自动诊断、自动修复、验证和复盘状态。
- 展示自动发现的问题进入了哪个 Case。
- 展示哪些操作需要人工审批，哪些已自动完成。
- 展示进化提案来自哪些失败/复盘。

产出：AIOps 闭环从“功能存在”变成“过程可见”。

## 当前优先级

建议按以下顺序实施：

1. IA-1：导航和入口边界收口。
2. IA-2：全栈监控大屏第一版。
3. IA-3：运维工作台主流程强化。
4. IA-4：平台控制台重构。
5. IA-5：自动化闭环展示。

## 验收标准

- 用户进入首页后，能看懂当前平台状态和下一步动作。
- 运维工作台一级入口不超过 4 个主线入口。
- 全屏大屏至少覆盖主机、Kubernetes、网络设备、闭环处理和拓扑准确性。
- Kite/Hermes/拓扑不再作为孤立功能到处出现，而是从上下文进入。
- 平台控制台能清楚区分智能能力、进化治理、平台运维。
